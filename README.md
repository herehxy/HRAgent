# 人才库智能体（HR 工作台）

**一档多投**的企业人才库：一个人只有一份档案，可以投多个岗位、多次投递、多版简历；
系统只给建议，**HR 确认才生效**；**不淘汰任何简历**。

本机 Web 工作台 + 本地小模型 + 可审计的写操作，全部离线内网运行。

## 一、六条硬约束（代码层面的不变式，不是口号）

| # | 约束 | 在代码里怎么保证 | 端到端断言 |
|---|---|---|---|
| 1 | **不丢件** | 附件先落盘归档再解析；解析失败照样建档并标「待人工判读」；每封邮件都写收信台账 | C / R |
| 2 | **零重复** | 三层去重：`message_id` → `SHA256(附件)` → `identity_key`（内容层）；**先判重再落盘**，原件区不会出现台账无记录的野文件 | B / H / R |
| 3 | **反幻觉** | 每条技能必须能定位到简历原文片段，否则 `verified=0`、不计入岗位命中，仅留待人工核对 | D |
| 4 | **只建议不决定** | 模型拿不到任何直接写库的路径；写类工具只产出 `proposals`，经 `actions.apply_proposal` 由 HR 确认后执行 | K / M |
| 5 | **合规屏蔽** | 民族/婚姻/生育/宗教/健康/身份证/住址/政治面貌/身高体重/照片在**进入任何模型之前**被替换；出生年份不写入结构化档案、不参与匹配。**性别**只取简历**明写的标签行**（绝不推断、不猜）、筛选开关出厂关闭、**永不进入评分** | E / N / S |
| 6 | **单角色 + 全程留痕** | 只有 HR 一个角色，不分子集权限、不做按角色脱敏；手机/邮箱**加密存储**但完整展示，密文与盲索引不下发前端；查看/改档/改阶段/确认提案/重复附件未落盘/性别开关切换全部落审计 | M / N / P |

边界同样明确：系统**没有硬删除入口**——岗位只能**停用**（历史投递必须留得住）；
来源文件夹里的文件可以"移走"，但只是移进回收目录 `data/removed/`（**可原样恢复**），不是物理删除；
候选人档案本身没有删除入口。**不自动发拒信、不发任何对外通知**，相关工具直接在工具层被禁用（`DISABLED_TOOLS`）。

## 二、快速开始

```bash
PY=/Users/hxy/.workbuddy/binaries/python/envs/default/bin/python

$PY cli.py init                     # 建库、写入岗位尺子、创建 HR 账号（内置样例简历在 data/resumes/，无需脚本生成）
$PY cli.py fixtures                 # 生成 8 封测试邮件（覆盖重复/无附件/损坏附件等）
$PY cli.py ingest --folder data/resumes   # 手工导入简历目录（只分析、不自动归岗）
$PY cli.py mail                     # 邮箱收简历（eml 演练 / imap 实收）
$PY cli.py index                    # 建向量索引（模型不可用时自动降级为哈希向量）
$PY cli.py report                   # 文字报表
$PY cli.py serve --port 8091        # 打开 http://127.0.0.1:8091
$PY cli.py doctor                   # 环境体检（模型/向量/解析/邮箱/本体/密钥/权限）
$PY cli.py majors                   # 查看已收录的学科目录（门类 → 一级学科）
$PY cli.py domains                  # 查看可选领域包（财务/数字化/检验检测…）
$PY cli.py import-domain 财务 --dry-run   # 预演导入领域包（不带 --dry-run 才真写入）
$PY cli.py selftest                 # 端到端自检：384 条断言，全部为真实调用
$PY tests/ui_probe.py --url http://127.0.0.1:8091   # 界面交互态截图验收（需先起 CDP Chrome）
```

其余：`search`（技能/语义召回）、`audit`（操作审计）。

**第一次使用建议顺序**：`init` → `serve` → 在界面「岗位管理」建好岗位（只写岗位名 + JD，不需要部门）→ 在「邮箱配置」填 IMAP 并点「测试连接」保存 → 点「收取简历」。

两个实用开关：

- `TP_DB_PATH=/tmp/demo.db $PY cli.py serve` —— 指向另一个库，演练/验收时不碰真实人才库；
- 界面每一页都有独立地址：`#pool` 人才库、`#archive` 归档、`#chat` 智能助手、`#org` 岗位管理、
  `#props` 提案与审计、`#search` 检索、`#mailcfg` 邮箱配置、`#sys` 系统说明，刷新不回首页、可直接发给同事。
  投递管道不再是独立页（v1.7.2）：以折叠条形式内嵌在人才库列表上方，旧地址 `#pipe` 自动落回人才库。

## 四、数据模型：人 / 投递 / 附件 三级分离

| 表 | 粒度 | 关键点 |
|---|---|---|
| `candidates` | 一个人一条 | `identity_key` 唯一；手机号与邮箱**加密存储**；软合并用 `merged_into`，不物理删除 |
| `applications` | 一次投递一条 | `tier_suggested`（系统建议）与 `tier_final`（HR 确认）**分列**；`stage` 走招聘管道；`job_id` 可空 = **所属岗位待指定** |
| `documents` | 一份原件一条 | `file_hash` 唯一（幂等去重的唯一依据）；`parse_ok` 记录解析是否成功；原件路径留档 |
| `departments` | 一个部门一条 | **2026-09 起界面不再使用**：岗位只写名称 + JD，部门概念退出产品界面；表与 `/api/departments` 接口为兼容旧库保留（新建库为空表），不参与任何评分/路由 |
| `jobs` | 一个岗位一条 | `dept_id` 兼容旧库保留（新岗位一律为空）；岗位自带一份 JD 尺子（`jd_json`）；**只能停用，不能删除** |

配套：`skills` / `candidate_skills`（带证据与 verified 标记）、`tags` / `candidate_tags`、
`email_messages`（收信台账）、`audit_log`、`agent_runs`、`proposals`、`users`、`sessions`、`settings`、`embeddings`。

### 岗位管理（HR 自己维护）

- 界面「岗位管理」可以新增岗位（**只写岗位名 + JD**，不需要部门）、**停用 / 重新启用**；
- 停用是软删（`active=0`，状态置「停用」）：已投该岗位的简历、投递记录、审计全部保留，
  列表里仍可查看，但**不再接收新的归岗**；
- 停用后再启用不会丢任何关联数据，历史投递的 `job_id` 一直指向该岗位。
- 每个岗位的 JD 除了技能/学历/年限，还可以写**专业需求**（学科名清单，带目录候选下拉）。
  加新行业、新岗位**不需要改代码**：学科来自 `config/majors.json`，行业技能来自
  可按需导入的领域包 `config/domains/*.json`——完整口径见 **10.5**。

### 简历怎么归到岗位（这是全系统唯一的归岗口径）

| 来源 | 是否自动归岗 | 规则 |
|---|---|---|
| **邮箱收信** | 看标题 | 邮件标题里出现某个**在招**岗位名（全称优先，其次去括号的核心词）→ 归到该岗位，并用该岗位的 JD 评分；标题没有岗位名、或岗位已停用 → 落「所属岗位待指定」 |
| **文件夹上传 / 手工导入** | **不归岗** | 只做解析、分级、建档，投递一律是「所属岗位待指定」，由 HR 事后在界面上指定 |

设计取舍：标题归岗解决"一个收件箱收多个岗位简历"的实际问题；上传不归岗是因为
文件夹里往往是混合批次，按标题猜岗位比留空更糟。两条路径都**只做建议性归岗**，
不改变「人 / 投递 / 附件」三级结构，也不影响任何去重判断。

### 三层去重（顺序很重要）

1. **邮件层** `message_id`：同一封邮件被重复拉取 → 不重复记账；
2. **文件层** `SHA256(附件)`：同一份简历换文件名再投 → 不重复落盘（**判重在落盘之前**，否则原件区会留下台账查不到的副本）；
3. **内容层** `identity_key`：同一个人换简历版本 → 不新建投递，只把新版本作为附件归档。

内容层命中后：**同岗位近期重复投递**合并为「新版本附件」；若 HR 已确认过档位，**绝不覆盖**，只追加文档并写审计。
脱敏手机号（`138****1234`）只有前 3 后 4 是真实信息，**不作为身份依据**，避免把两个不同的人误并成一档。

### 候选人软归档与批量归档（v1.4 立，v1.5 补批量与按年）

- 入口：人才库卡片上的「归档」按钮；批量入口在人才库工具条（**勾选若干人归档** / **按年份归档该年以前**）；
  归档结果集中在导航的「归档」页（`#archive`）展示；
- 效果：归档后该候选人**不再出现在人才库默认列表与三类检索结果**（技能召回 / 语义召回 / 相似人才）里；
- **不是删除**：档案、投递、附件、审计全部原样保留，`candidates.archived_at` 只是一个时间戳，
  「归档」页点「取消归档」即恢复展示，完整档案在归档期间也仍可直接访问；
- 留痕：归档与取消归档各写一条 `archive` / `unarchive` 审计（谁、何时、做了什么）；
  **批量归档逐人写审计**，不是一个批次号糊过去——追究到人时能直接举证；
- 统计口径不变：顶部统计卡仍按全量人数计算，归档只改变"列出谁"，不改变任何档位与评分。

**为什么需要批量归档（使用场景决定）**：本系统按年使用，第二年的简历会和第一年的混在同一列表里。
HR 需要一次把「2026 年以前的投递」整体收起，而不是点几十次单条归档。
`POST /api/candidates/archive-batch` 支持 `ids`（勾选清单）与 `before_year`（按年）两种口径，
返回 `changed` / `skipped`（已归档或不存在的人被跳过而不是报错，操作天然幂等）。

### 归档满 30 天才彻底删除（v1.5）

- **删除不是立即删**：归档只是第一步。归档满 **30 天**（`db.PURGE_AFTER_DAYS`）后，
  才允许把数据库记录**彻底删除**、原件移入回收目录 `REMOVED_DIR/purged`；
- **为什么要一个 30 天冷静期**：误归档、误操作、HR 改主意回头找人，这些都真实发生。
  立即删除是不可逆的；留 30 天窗口后，**「取消归档」随时可恢复**，风险敞口被压到最小；
- **未满 30 天点删除会被明确拒绝**：接口返回 **409** 并告知剩余天数（`/api/candidates/{cid}/purge`），
  不是静默失败、也不是悄悄降级成归档；
- **到期前主动兜底**：服务启动跑一次 `purge_due_candidates()`，之后由 **24 小时守护线程**周期清理，
  不需要 HR 记得手动点（`/api/archive/purge-due` 也留了手动触发入口，`cli.py purge` 同理）；
- **彻底删除也留痕**：`purge_candidate` 审计记录被删的人与文件清单；档案正文虽然删了，
  「谁在什么时候以什么规则清了什么」仍可追溯——这是合规场景的硬要求；
- 归档页每人显示**剩余天数与到期日**（`archive_meta()`），并只对已到期的人显示「彻底删除」按钮，
  避免出现"按钮点下去必然报错"的假入口。

## 五、分级口径（`config/tiers.json`，可改）

| 档 | 含义 | 口径 |
|---|---|---|
| **A 优先面试** | 必需技能全中 + 学历/年限达标 | score ≥ 0.85 |
| **B 建议面试** | 基本匹配，缺 1 项可培养 | score ≥ 0.65 |
| **C 储备** | 条件偏弱但有潜力 | score ≥ 0.45 |
| **D 暂不匹配当前岗位** | 建议转人才库/其他岗位，**简历保留** | 其余 |

评分构成：学历 0.25 / 年限 0.25 / 必需技能 0.35 / 加分项 0.15。学历或年限硬性不达标直接进 D；
缺失 2 项以上时按分数落到 C 或 D。解析失败另置 **待人工判读** 标记，降到 D 但**不丢弃**。
每条档位都带命中证据与缺失项，可逐条核对——分数不是黑箱。

## 六、智能体：小模型 + 工具集 + 治理

- **工具集**（`app/agent/tools.py`，共 27 个）：20 个可调用（检索与查看 12 / 计算生成 3 / **写类 5**），7 个**直接禁用**（对外发送、删除、淘汰、导出外网）。
- **写类工具不写库**：返回 `pending_confirmation`，并明确告知模型「尚未生效，不要声称已完成」。
- **调用循环**（`app/agent/loop.py`）：最多 5 轮工具调用，超轮强制收敛；全量写入 `agent_runs`（问题、工具链、轮数、token、耗时、模式）。
- **降级不失效**：模型不可用时走确定性规则路由，用关键词 + 技能本体识别意图，调用同一批工具作答，
  **工具链同样留痕**；「同时具备 A、B」无人满足时自动放宽为「任一命中」并如实说明，不会只回一句"没有"。

### 6.1 问岗位能答上来（v1.6）

「现在发布了几个岗位」「某岗位要求是什么」这类问题，走 `list_jobs` 工具读真实库作答，
**不靠模型凭印象说**——凭印象就会编出并不存在的岗位名。

口径与归岗用的 `routable_job_ids` **完全一致**：在招 = 岗位本身启用
（2026-09 起没有部门概念，历史上的"部门停用连带不可收"口径已随之取消）。
`include_inactive=True` 时仍可查全部（停用是软删，不是消失）。

### 6.2 对话历史不点清空就不会丢（v1.6）

每轮问答**本来就落库在 `agent_runs`**（问题、答案、工具链、轮数、token、耗时）。
过去"一刷新历史就没了"不是没存，是前端把对话放在内存数组里、**从来没去读**。
现在进入「智能助手」页即从 `/api/agent/history` 回填，因此刷新页面、换设备、重启服务后对话仍在。

**「清空」是软清空，不是物理删除**：只推进一个"清空点"（`chat_cleared_run_id`）并开出
**30 天保留期**。理由与档案归档、来源文件移入回收目录完全一样：`agent_runs` 同时承担
token 成本核算与治理审计（这一问调了哪些工具、是否走到降级、有没有越权尝试），
删掉它等于把"这段对话花了多少、系统做了什么"一起抹了。

> 清空点以**运行序号**为准而不是时间戳：`now()` 只精确到秒，而"点清空 → 同一秒内再问一句"
> 是很自然的操作（规则路由下几乎必然同秒），用 `ts > 清空时间` 会把刚问的那句话判成
> "在清空点之前"，历史里看不见。序号自增、严格单调，没有这个歧义。

### 6.3 清空后 30 天内可恢复，到期自动清理（v1.6）

**口径与档案的"归档满 30 天才彻底删除"完全一致，共用同一个 `db.PURGE_AFTER_DAYS`**——
产品里的"缓冲期"只应该有一个数字，两个地方各写一个迟早会漂移。

| 阶段 | 数据 | 界面 | 可逆性 |
| --- | --- | --- | --- |
| 点「清空」 | `agent_runs` **全部保留**，只写清空点 + 到期时间 | 对话归零，顶部提示条写明"将于 X 自动清理（还剩 N 天）" | 「恢复对话」一键找回 |
| 保留期内（0–30 天） | 同上，逐条记录与工具链都还在 | 提示条 + 「恢复对话」按钮常驻 | 同上 |
| 到期（第 30 天） | 后台任务先写 `chat_purge` 汇总审计，**再删明细** | 提示条消失，恢复入口不再出现 | 不可逆 |

四个设计取舍，写在 `app/db.py` 的 docstring 里也在这里留一份：

1. **多次清空以最后一次为准**。清空点取当前最大运行号，保留期从这次清空重新起算——
   "只要还在清空，就不会有东西被清掉"。方向是**保留更久**，绝不提前删；
2. **到期后到真正执行之间还有一段窗口，这期间仍允许恢复**。后台任务每 24 小时才跑一次，
   `restorable` 因此只看"清空点还在不在"，不卡到期时间：系统还没删的，人就该能捞回来。
   宁可让人多救一次，也不抢在人前面做不可逆决定；
3. **先汇总再删明细**。删除前把条数、token 合计、运行号与时间区间写进 `chat_purge`；
   被抹掉的只是逐条明细，"这段时期一共跑了多少次、花了多少"这个总量证据留得住；
4. **没有可解析的到期时间就不动手**。宁可永不自动删，也不因为脏数据误删一批记录。

审计链完整且**永久保留**：`chat_clear`（谁什么时候清空）→ `chat_restore`（又什么时候恢复）
→ `chat_purge`（系统什么时候清掉、清掉多少），三条一起才说得清一段行为。

触发方式与归档彻底删除对称：服务启动跑一次 + 每 24 小时守护线程一次，
可手动执行 `POST /api/agent/purge-due` 或 `python cli.py purge-chats`。

> 倒计时用**向上取整**，与归档页 `days - (now - ts).days` 同一口径：刚清空显示"还剩 30 天"。
> 向下取整会因为"30 天整减去几毫秒的执行耗时"当场显示 29 天，读起来像系统偷偷少给了一天。

### 6.4 哪些事不通过对话做（v1.6，这是设计选择不是能力缺口）

「帮我抓取文件夹最新简历」「改一下文件夹路径」「改一下邮箱」「抓取邮箱最新简历」这类请求，
智能助手会**如实说明它不接**，并指向「导入与来源」页让 HR 自己点。理由三条：

1. **有副作用**：抓取会读外部邮箱/磁盘、写库、改索引，是"动作"不是"回答"。
   把它挂在一句话后面，等于让一句可能被误解的自然语言直接产生外部效果；
2. **要审计凭证**：收信用的邮箱授权码、来源目录路径属于配置与凭据，
   改它们必须留下"谁改的、改前是什么"，走界面按钮才有人为确认这一环；
3. **与产品红线一致**：本系统"系统只给建议、HR 确认才生效"——
   抓取与改配置恰恰是最不该由模型代劳的两类操作。

**这与模型大小无关**：换 32B、72B 也一样不开放。模型大小决定的是"读得懂多少、答得多准"，
不决定"该不该由对话触发有副作用的操作"。

至于**14B 够不够用**（用户的实际问题）：够。Qwen3-14B 在本系统三条路径上都实测通过——
对话、工具调用（function calling 选对工具并传对参数）、JSON 回填（抽取与分析结果的结构化输出）。
本系统对模型的要求本来就压在"读懂 + 选工具 + 吐 JSON"上，真正的判断（分级、归岗、检索）
都在确定性代码里，所以 14B 这个量级是合适的；上更大模型带来的收益主要在长文本理解与
复杂推理，不是本工作台的瓶颈。

### 接入模型（四选一）

| 方式 | 配置 | 适用 |
|---|---|---|
| Ollama 本地 | `preset: "ollama_14b"` / `"ollama_8b"` | 数据不出内网；16GB 机器建议 8B |
| 内网 vLLM | `base_url: http://<gpu-host>:8000/v1` | 量产、信创私有化 |
| **通义千问（Qwen3-14B）** | `model: "qwen3-14b"` + `base_url: https://dashscope.aliyuncs.com/compatible-mode/v1` | 快速验证；与信创私有化前的效果对照 |
| DeepSeek | `preset: "deepseek"` + 密钥 | 快速验证 |

优先级：环境变量 > `config/secrets.json` > `config/model.json`。
密钥只写 `config/secrets.json`（已 gitignore）；**不要写进代码或提交仓库，泄露立即轮换**。
访问 `127.0.0.1` 的调用会自动绕过系统代理（`app/net.py`），避免代理把本机模型请求拦成 502。

**"换模型"只改一个字段，但要知道现在用的是哪一代**。同一条百炼通道上，
`qwen3-14b`（当前配置）、`qwen3.5-*`、`qwen3.6-*`、`qwen3.7-*`、`qwen3.8-*` 全代都可调用
（`GET /v1/models` 会列出该 Key 可见的全部 id，`cli.py doctor` 会核对配置的模型是否就绪）。
本工作台对模型的要求压在"读懂 + 选工具 + 吐 JSON"，14B 这个量级够用，
上更大模型买到的是长文本与复杂推理能力，不是本工作台的瓶颈——
**要换成更大/更新的模型，只需把 `model` 改成对应 id，业务代码一行不动**。
`_apply_provider_quirks()` 的 `qwen3*` 前缀判断对上述各代都生效（思考模式开关不用手配）。

> 当前生效的是什么、走的是哪条通道、有没有在降级，**在界面上就能看到**：
> 「系统说明」页 →「运行环境」卡（对话模型 + `base_url`、向量模型可达状态、
> 索引实际使用的模型）。CLI 对应 `python cli.py doctor`。

**Qwen3 有一个必须知道的服务端约束**：百炼的 OpenAI 兼容接口在**非流式**调用下
**强制要求 `enable_thinking=false`**，不传就直接返回 400
（`parameter.enable_thinking must be set to false for non-streaming calls`）。
本工作台走的就是非流式（要拿完整 JSON 回填），所以 `app/agent/llm.py` 里的
`_apply_provider_quirks()` 会对 `qwen3*` 模型**自动补上 `enable_thinking=False`**，
需要时可用 `cfg["extra_body"]` 覆盖。这一层不改业务代码、只在通道层适配，
所以换任何一家 OpenAI 兼容服务都不用动抽取与评分逻辑。

## 七、检索

- **技能召回**：走本体归一，`mode=all`（全部命中）/ `mode=any`（任一命中）；本体外的词如实标出，不假装认识；每条结果都带原文证据。
- **语义召回**：向量相似度；embedding 服务不可达时自动降级为**本地哈希向量**（词面相似度），并在返回里说明用的是哪个模型。
- **相似人才**：按档案向量找同类背景的人。
- **结果直接带联系方式**：三条召回路径的返回值都含明文手机号与邮箱（与人才库列表同一套展示口径），
  检索页可直接拨号/发信、一键复制，不用再逐个点开完整档案。解密只发生在接口层，
  密文列、盲索引、身份键一个都不出现在检索结果里（自检有断言）。
- **没有「重建索引」按钮**：导入新简历后由 `server._auto_index()` 自动做**增量**索引
  （`build_index(force=False)`，只处理画像新增/变更的人）。比对基准取"实际落库的模型名"
  （`search.effective_model()`）而不是配置里的模型名——否则 embedding 服务降级时
  哈希向量落库、却拿配置名去比对，会每次都全量重算，「增量」名存实亡。

## 八、简历原件与来源可见性

### 8.1 原件：两种打开方式

| 能力 | 说明 |
|---|---|
| **在线打开** | `GET /api/documents/{id}/file?inline=1`，PDF/文本直接在浏览器里看（`Content-Disposition: inline`） |
| **下载原件** | `GET /api/documents/{id}/file`，按附件下载（`Content-Disposition: attachment`） |
| **路径防护** | 只允许发本仓库目录下的文件：`realpath` 必须是仓库根的子路径，否则 403；不存在的附件 404 |
| **相对路径兼容** | 老数据的 `archived_path` 是 `data/archive/xxx` 这类相对写法，会按仓库根解析——服务换工作目录启动也不丢原件 |
| **留痕** | 每次预览/下载都写审计（`preview` / `download`），"谁能看别人的简历"可追溯 |

**MIME 必须落真值**：入库时按后缀写 `mime`（PDF → `application/pdf`），下载接口也按同一张表
（`parse.MIME_BY_EXT`）兜底。浏览器只有拿到 `application/pdf` 才会就地渲染，
拿到 `application/octet-stream` 就只会弹下载框——**入库写 `None` 会让"在线预览"这个能力形同不存在**。

### 8.2 来源文件：**导入之前**也能看、能下、能批量下

凭文件名猜"这份该不该导"是不现实的。所以来源文件夹里的文件，**入库与否都能先看内容**：

| 能力 | 接口 | 说明 |
|---|---|---|
| 在线预览 | `GET /api/sources/file?name=xxx&inline=1` | 尚未入库的 PDF 也能直接在浏览器里打开 |
| 下载 | `GET /api/sources/file?name=xxx` | 按附件下载 |
| **多选打包** | `POST /api/sources/bundle` | 请求体 `{names:[...], document_ids:[...]}`，已入库与未入库可混选，一次打成 zip |

- **打包用请求体而不是逗号拼接的查询串**：简历文件名里出现逗号是常事，`a,b.pdf` 拼接会切错。
- 打包三重上限：单次 ≤ 200 份、合计 ≤ 500MB、重名自动加序号（避免 zip 内互相覆盖）。
- **一份取不到不整体失败**：跳过并在响应头 `X-Skipped` / `X-Skipped-Detail` 里如实列出，
  否则勾了十份、其中一份原件丢了，整批都下不来，HR 还得逐个试。
  头部只放 ASCII（中文走百分号编码），前端解码还原——**HTTP 头里直接写中文会让整个下载 500**。
- 来源文件的守卫与原件同源：只认**纯文件名**（拒绝任何路径分隔符与 `..`）、
  只认与解析一致的后缀白名单、`realpath` 必须落在配置的来源目录内。

### 8.3 归档：任何来源都要落一份副本

邮件附件与**文件夹导入同样**复制进原件区（`file_path` 记原始出处，`archived_path` 指向归档副本）。
早先文件夹导入直接拿扫描目录里的路径当 `archived_path`，**HR 清理或挪动一次来源目录，库里的原件就集体 404**——
而本模块的设计前提正是"原件区只增不改"。

### 8.4 来源可见性

「导入与来源」页显示：文件夹**绝对路径**（可直接编辑保存）+ 文件清单（大小/修改时间/是否已入库/属于谁），
邮箱则显示**抓的是哪个账号与服务器**、口令是否已设置（只给布尔，不回显），
并展示最近一次导入的**逐份明细**（含附件编号，明细行可直接预览/下载）。

> 界面入口与后端接口必须成对存在。本页此前出现过"后端字段与接口都在、界面上没有输入框"的情况——
> 所以自检里同时有 **接口断言**（响应体内容正确）与 **界面断言**（DOM 上真有那个入口）。

### 8.5 来源文件删除：移进回收目录，不是抹掉

来源目录里会混进与招聘无关的文件（随手放进去的书、扫错的页），所以给了删除入口。
但它**不是物理删除**：

| 能力 | 接口 | 说明 |
|---|---|---|
| 移走 | `POST /api/sources/remove` | 请求体 `{names:[...]}`；实际动作是 `shutil.move` 到 `data/removed/YYYY-MM/` |
| 看回收目录 | `GET /api/sources/removed` | 列出被移走的文件（文件名/大小/移除时间/操作人），并回带**最近一次移除批次** |
| 恢复 | `POST /api/sources/restore` | 请求体 `{names:[...]}`；**同名冲突直接拒绝**，不覆盖现有同名文件 |

三条关键实现约束：

1. **移走前先补归档**。老库（v0.1 迁移）里有一部分 `archived_path` 是**指向来源目录**的
   （`data/resumes/xxx.pdf`），直接移走会让"下载原件"变成 404——看起来像简历丢了。
   所以移走前先给这类文件在原件区补一份副本并改库指向，**原件区只增不改**这条不变式不能破。
   自检里专门断言"移走之后原件仍可下载"。
2. **不删库里的投递与档案**。来源文件没了，人才库里那条记录还在（`documents` 行不删），
   只是"原件路径"指向回收目录——历史投递必须留得住。
3. **逐份写审计**（`remove_source` / `restore_source`），二次确认框里明确写出"移入回收目录、可恢复"，
   避免 HR 以为这是不可逆操作而不敢用。

### 8.6 体积上限：文件夹导入和邮件路径**同一把尺子**

`max_attachment_mb`（默认 20MB）此前只在邮件路径生效，文件夹导入**完全不校验**——
于是把一本 17MB 的书放进 `data/resumes/` 也能进来，解析失败后落成一条空档案，污染人才库。

现在两条路径共用同一个上限：超限文件**跳过、不删、原样留在来源目录**，写一条
`oversize_skipped` 审计，并在导入报告与界面上如实给出 `skipped_oversize` 计数。
来源清单里超限文件带醒目标记（`over_limit`），**导入之前**就能看出"这份太大，系统不会收"。

## 九、邮箱配置（界面里配，不用改文件）

界面「邮箱配置」一页可以完成全部收信设置，保存即生效：

| 配置项 | 说明 |
|---|---|
| 收信模式 | `eml`（读本地 .eml 目录，演练用）/ `imap`（连真实邮箱）/ `off`（关闭收信） |
| eml 目录 | 演练模式下读取的目录（默认 `data/mail_in`） |
| 本地文件夹 | `folder_dir`：文件夹导入源（默认 `data/resumes`）。界面里能看到它的绝对路径与文件清单 |
| IMAP 服务器 / 端口 / SSL | 如 `imap.exmail.qq.com` / `993` / 开启 |
| 账号 | 收简历的专用邮箱地址 |
| 口令 | 保存到 `config/imap.secret`，权限 `0600`，**不入版本库**；也可改用环境变量 `TP_IMAP_PASSWORD` 或系统钥匙串，页面会显示「已设置 / 未设置」，**不回显口令本身** |
| 收件夹 | 默认 `INBOX` |
| 附件白名单 | `.pdf .docx .doc .txt .md`，可增删 |
| 附件体积上限 | `max_attachment_mb`（默认 20）。**邮件与文件夹导入共用这一把尺子**，超限的跳过并如实计数 |
| 归岗窗口 | 同岗位重复投递合并为「新版本」的天数（默认 30 天） |

**服务商预设**（`GET /api/mailbox/presets`）：腾讯企业邮、QQ 邮箱、网易 163、阿里云企业邮、
Outlook、Gmail——一键把服务器/端口/SSL 填对。**端口填错是"测试连接永远失败"的头号原因**，
与其让人去查文档，不如内置一张正确的表。

### 9.1 「配了没反应」的根因，直接在界面上说清楚

最常见的自诊困难不是配置错误，而是**配了却和当前模式不匹配**：模式还是 `eml`（演练，读本地
`.eml` 目录），却填了 IMAP 账号和授权码——点「收取简历」当然毫无反应，因为**它压根没连邮箱**。

这类提醒不写在文档里、也不靠 HR 自己回想，而是由后端**一处产出**（`_mailbox_warnings()`），
保存/测试/读取三个接口**共用同一份**下发给界面：

| 场景 | 界面上的原话（要点） |
|---|---|
| `eml` 模式却填了 IMAP 账号 | 「当前是 eml 演练模式：收取时读的是本地 .eml 目录，不会连真实邮箱。要真正收信，请把模式改为 imap 并保存」 |
| `imap` 模式但口令/授权码为空 | 明确指向授权码，而不是含糊说"缺少凭据" |
| 国内邮箱用登录密码 | 提醒**必须用授权码**（QQ/163/企业邮在开启 IMAP 后单独生成，登录密码一律失败） |

同一份提醒也复用在「测试连接」：失败时给下一步指引，成功时也说明连的是哪个账号——**不静默**。

- 「**测试连接**」按钮：按填写的参数真连一次 IMAP 并选收件夹，成功/失败都会给出具体原因；
  **测试过程只报状态，不回显也不记录口令**。
- 「**先看邮箱里有什么**」按钮（`POST /api/mailbox/preview`）：收信**之前**先只读看一眼——
  连的是哪个账号、最近几封的主题/发件人/时间/附件名、哪几封含简历。
  只 `FETCH (BODY.PEEK[HEADER.FIELDS ...] FLAGS)` 与 `BODY.PEEK[STRUCTURE]`，不下载正文、不改已读标记。
  eml 演练模式下直接列本地目录。
- **只读收信**：`SELECT` + `BODY.PEEK[]`，不删信、不置已读、不改动服务器上的任何邮件；
  收信游标存在库里（`email_messages`），不会重复拉取同一批邮件。
- 配置写到 `config/mailbox.json` + `config/imap.secret`；**任何写入口都不接受明文口令落进 mailbox.json**。

## 十、岗位 JD（评分尺子）

岗位不再只是一个名字：新增岗位时可直接写下这个岗位的 JD，改档与评分都按它算。

| 字段 | 作用 |
|---|---|
| 必需技能 | 参与必中判定与命中计数（走技能本体归一） |
| 加分技能 | 只加分，不构成"缺项" |
| 最低学历 | 大专/本科/硕士/博士，低于门槛扣分并记为风险 |
| 最低年限 | 工作年限门槛 |
| **专业需求**（v1.7） | 学科名清单（如 材料科学与工程 / 仪器科学与技术），**只用于方向判定与解释，不构成硬门槛**；填错位置会被当场提示（见 10.4） |
| 职责说明 | 自由文本，供 HR 与模型分析参考 |

- 接口：`GET /api/jobs/{jid}` 读岗位与 JD；`POST /api/jobs/{jid}/jd` 改 JD。
- **只改传了的字段**：只提交 `years_min` 时，必需技能不会被清空；
  显式传空值（`[]` / `""` / `0`）才是"去掉这项门槛"。
- **影响边界**：JD 改动**只影响之后新入库的投递评分**，已入库的投递档位不会被追溯改动；
  每次变更都写审计（含变更前后两份尺子），接口返回里也会明确这句话。
- **改完 JD 界面上会主动引路**：保存响应回带 `can_regrade` / `regrade_endpoint` 与一句话提示，
  弹层里直接给出「按新尺子重新分析这 N 条」的按钮。否则 HR 改完 JD 会觉得"匹配结果没变，
  是不是改动没生效"——**这不是功能问题，是没告诉人下一步该做什么**。
- 岗位列表下发 `jd_json`，列表页直接渲染 JD 摘要，一眼看出每个岗位的尺子是什么。

### 10.1 重新分析（改完 JD 后追溯已有投递）

接口：`POST /api/jobs/{jid}/regrade`，请求体 `{"apply": false}`。默认**预演**。

| 模式 | 行为 | 写入 |
|---|---|---|
| `apply=false`（默认） | 完整算一遍差异，逐人给出「存储值 → 重算值」 | 业务数据**一个字都不写**，只留一条 `regrade_preview` 审计 |
| `apply=true` | 把差异落库（分数/建议档位/命中缺失/理由/分解） | 逐条写审计（含变更前后），再写一条 `regrade_batch` 批次审计 |

三条硬约束：

1. **绝不覆盖 HR 已确认的结论**。`tier_final` 已填或状态为「已确认」的投递，只记差异、不改数据，
   弹层里明确标注「HR 已确认，未改动」。系统只给建议，决定权在 HR。
2. **只走规则通道、不调模型**。可重复、可预期——不把"这台机器当时连不连得上模型"混进
   "改 JD 之后变成什么样"的结论里。当初走模型通道抽取的投递会标注 `old_extract_mode`，
   说明差异**不全部来自 JD**。
3. **默认先看不改**。一次误点就把全岗位建议档位改掉，代价太大，所以先给差异、看过再点「应用」。
   界面上的应用按钮还会标明"改 N 条"。

**为什么从简历原文重跑，而不是直接读库里的画像？**
`certificates`（证书加分）、`unverified_skills`、`skill_detail`（技能证据）这三样**都没有落库**。
若只读库里那几列基础字段去重算，证书加分会被当成"不存在"，分数凭空往下掉——
**看起来像"改了 JD 导致降档"，其实与 JD 无关，是画像被读残了**。
所以统一从 `documents.raw_text` 重跑一次规则抽取，保证前后两次评分用的是同一套画像口径。

无法重算的情况如实列出（`cannot_regrade`）：简历原文缺失或当初解析失败（如扫描件 PDF）。
这类投递的分数保持原值不变，不会因为"算不出来"而被清零。

**落库闭环怎么验的**：应用之后再跑一次预演，「将变化」必须归零。
只比对弹层文案会被"界面改了、库没改"骗过去，所以界面验收用的是这个闭环口径。

### 10.2 待指定投递的岗位建议（v1.5：逐岗位轮询，不再用默认尺子）

**先说清楚旧口径错在哪。** 归岗的自动通道原本只有一条：**邮件标题写了在招岗位名**。
标题没写岗位名的邮件、以及文件夹导入的简历，一律落「所属岗位待指定」，
然后被 `config/jd.json` 这把**默认尺子（材料类）**统一试算打分。
后果是：一位 Java 后端工程师在材料尺子下"全部不命中 → D 档低分"，
列表上完全看不出他是干什么的——**把人判成了"不合适"，其实只是"尺子不对"**。

v1.5 把这条口径整个换掉，现在有且只有两条通道：

| 通道 | 适用 | 做法 |
|---|---|---|
| **标题归岗**（保留） | 邮件标题里写了在招岗位名 | 直接归到该岗位，**不轮询**；写审计 |
| **逐岗位轮询**（新） | 标题没写岗位名、文件夹导入 | 对**每一个在招岗位**各自试算，取最匹配者作为**建议岗位** |

**关键实现细节（决定了它准不准）：**

1. **每个岗位各自抽取一次，不是"抽一次、多岗位打分"。**
   技能识别依赖**该岗位的 JD 词表**——材料岗的 JD 里有「真空熔铸」，
   软件岗的 JD 里有 `Java`/`Spring Boot`，同一份简历对两个岗位能识别出的技能本就不同。
   复用一份画像去打分，等于让软件岗拿着材料岗识别出来的技能清单做判断，
   必然漏判（这正是本轮修掉的缺陷 **#42**）。
2. **不再有"默认尺子"这条兜底路径。** 待指定投递不再被任何岗位的分数"默认判定"，
   而是轮询后给出建议；没有可用建议就老实停在「所属岗位待指定」。
3. **"是否适合"用技能命中判定，不用分数。** 学历达标、年限达标、格式完整
   也能把分数抬到 0.3 以上，单看分数会让一份财会简历被硬凑到某个岗位上。
   所以 `usable = bool(hit)`——**至少命中一项该岗位技能，才认为这份建议有意义**。
   分数与档位照常算，但它们是"命中之后解释有多匹配"，不是"要不要推荐"的门槛。
4. **建议岗位落库**（`applications.suggested_job_id`，v1.5）。入库时即算好并写入，
   列表接口直接读库（`source: "stored"`），只有存量的老数据才走实时兜底（`source: "live"`）。
   这样做的理由是**历史结论要稳定**：今天新增一个在招岗位，不应该让上周已归档的
   每条记录的判定结果跟着变。存量数据由启动任务 `regrade.route_pending()` 自动补齐升级。
5. **建议 ≠ 归岗**（红线未变）。卡片上显示蓝色芯片「建议岗位：软件开发工程师（0.86·A）」，
   HR 点「采纳建议岗位」才真正归岗，归岗时按该岗位 JD 重算档位并写审计；
   归岗后 `suggested_job_id` 置空（已确定岗位不必再建议）。
   技能栏也随之刷新（`persist_skills`），避免出现"命中里写着 Java、技能栏却没有 Java"这种自相矛盾。
6. **零交集就明说。** 与所有在招岗位都无交集时，卡片显示「与所有在招岗位均无交集，保持待指定」，
   **不硬凑**。

真实库实测效果：林一诺 → 工艺工程师（0.92·A）、沈亦风 → 软件开发工程师（0.86·A，命中
`Java` + `Spring Boot`）、另一位 Java 后端 → 软件开发工程师（0.86·A）；
周子墨、陆知行与所有在招岗位零交集，保持「所属岗位待指定」。

> 一句话概括本轮的修正方向：**从"一份简历配一把固定尺子"改成"一份简历对多个岗位逐个量，
> 取最合身的那件"**。人不该因为系统只有材料类尺子而被判成材料类不匹配。

### 10.3 三条分析路径一律按「对应岗位」（v1.6）

10.2 把**入库评分**的口径改对了，但当时漏了一件事：**下游三条分析路径没有跟着改**。
「档位解释」「岗位匹配分析」「面试题纲」各自直接读 `config/jd.json` 那把材料类默认尺子，
于是软件岗候选人点「档位解释」看到的还是材料岗的拆解、点「面试题纲」拿到的是
VAR 熔炼与金相分析的问题（缺陷 **#46**）。

现在三条路径统一走 `db.resolve_candidate_job()`，口径与归岗一致，**有且只有两级**：

| 优先级 | 条件 | 结果 | 界面标识 |
|---|---|---|---|
| 1 | 名下投递里有已归岗的（`job_id` 非空） | 用该岗位 | `已归岗` |
| 2 | 有建议岗位（`suggested_job_id`） | 用建议岗位 | `建议岗位（尚未归岗，采纳后转为已归岗）` |
| 3 | 都没有 | **如实报"尚无对应岗位"**，并给出下一步 | — |

第 3 条是重点：**宁可说"我判不了"，也不套一把不对的尺子**。
所以三个接口统一返回 `error` + `hint`（`hint` 是"下一步该怎么办"，
界面直接渲染在错误下面，模型也能把它当成可执行动作）。

每处分析结果都带 `job` 元信息，界面上先显示一行
**「档位解释针对岗位：软件开发工程师 · 已归岗」**——HR 一眼能看出这次用的是哪把尺子，
不用猜。

> 实测对照：同一时刻两位候选人，沈亦风（软件岗）拿到 Java/Spring Boot/Redis/分布式 的问题，
> 林一诺（工艺岗）拿到 VAR 熔炼、难熔合金热加工、金相分析、ANSYS 的问题，**互不串台**。

### 10.4 档位解释不只数关键词，还看专业方向（v1.6 立，v1.7 换学科目录）

**"缺哪几项技能"和"方向对不对口"是两件事**，混在一起说会给出误导性的结论：

- 缺技能是**深度问题**——培养、上手、给时间就能补；
- 方向不对口是**方向问题**——换一个岗位才有意义，培养补不上。

所以档位解释在关键词命中之外，加一块**方向匹配**，四个要素各有明确来源：

| 要素 | 来源 |
|---|---|
| 技能 → 大类映射 | 技能本体 `config/ontology.json` 的 `categories`（材料 / 工艺 / 表征 / 软件 / 管理），**本体优先于库表** |
| 岗位侧重大类 | 该岗位 JD 的必需技能 + 加分技能各自归类后按项数排序 |
| 候选人所长大类 | 候选人技能归类后按项数排序 |
| 专业方向（v1.7 改口径） | **学科目录 `config/majors.json` + 该岗位 JD 的 `must.major_required`**——不再从「专业」文本猜业务大类 |

v1.7 起结论不再是一句「对口/错配」，而是**渠道 + 置信度 + 依据**三件套：

| 渠道 | 触发条件 | 结论 | 置信度 |
|---|---|---|---|
| **大类** | 候选人专业能归到学科门类，岗位侧也有专业需求 | 门类与需求一致 → 对口；有交集 → 部分对口；无交集 → 错配 | 高 |
| **专业** | 精确命中 `major_required` 里的某个一级学科 | 部分对口（专业对上了，技能覆盖仍不足） | 中 |
| **词面** | 只在字面上部分重合（去壳后相似度 ≥ 0.55） | 部分对口 | 低 |
| **无** | 两边都无法判定 | **如实报「无法判定」**，并列出未能归类的原始术语 | — |

置信度**参与降级**：技能覆盖率低于 35% 时，即便方向对口也把结论降一档（对口 → 部分对口）——
避免出现"方向对了、技能只命中一项，却报对口"的过度乐观。

三条容易写错、已经踩过的口径：

1. **「其他」不进方向判断。** 「其他」的含义是"本体里没有这条技能、归不了类"，
   是**我们不知道它属于哪个方向**，不是"这个人擅长杂项"。把它算进"侧重"会出现
   「岗位侧重 其他（4 项）」这种没有信息量还误导人的结论——实测软件岗 5 项技能里
   4 项未归类时，「其他」一度排到侧重第一位。现在它被单独计出、如实说明，但不参与判定。
2. **本体要跟上岗位。** 本体的"软件"类原本 25 条全是工程仿真软件（ANSYS 等），
   通用开发技能（Java / Spring Boot / Redis …）在库里查不到 → 全归"其他" →
   软件岗的大类匹配整体失真（缺陷 **#48**）。v1.6 补齐 29 条通用开发技能，
   v1.7 再向前一步：**不再往主本体里硬塞**，改成按行业分包的**领域包**按需导入
   （见 10.5）。当前本体 277 条标准名 / 索引 838 键（缺陷 **#49** 归零）。
3. **专业需求是独立维度，不参与硬淘汰。** 岗位 JD 里「专业需求」是**一等字段**
   （`must.major_required`），不是门槛。理由：招聘公告几乎都写"XX 等相关专业"，
   写死会误杀跨专业候选人。它的用途只有两个——① 作为方向判定的依据；
   ② 在解释里如实呈现"这个人的专业在不在需求范围内"。
   **真正挡人的仍然只有学历与年限**（可量化、可申诉），其余都是分数与解释。

> 一个已经堵上的坑：HR 把学科名（"材料科学与工程"）误填进「必需技能」，会让一大批
> 非材料专业简历一律"缺必需技能"。现在保存 JD 时会**当场提示**（响应里的 `warnings`：
> 检测到技能框里出现学科名 → 建议挪到专业需求），是提示不是拦截——不替 HR 做决定，
> 但不让错误静默发生。

### 10.5 加岗位不用改代码：三条不变式 + 两个「只加数据」的地方（v1.7）

先前的做法是"岗位写死在尺子里"：新增一个财务岗，等于要在业务代码里再造一套分类；
而技能本体是开放集合，**永远补不到"补完"的那天**。所以 v1.7 把扩展面收敛成三条不变式：

| # | 不变式 | 反面（明确不做） |
|---|---|---|
| ① | **未收录 ≠ 判错**。本体里没有的技能如实标为「未归类/待补」，不改变这个人是否被判错的结论 | 把"本体里查不到"当成"这个人不合格" |
| ② | **方向判定锚在通用学科体系上**。用学科门类 → 一级学科（有限、官方收口、一次建成长期够用），不再自定义"材料/工艺/软件"这种业务大类 | 每来一个行业就临时定义一套大类 |
| ③ | **专业需求是一等字段且不进技能框**。学科名进 `must.major_required`，只影响方向判定与解释 | 把"材料科学与工程"当必需技能，非本专业一律"缺必需技能" |

落到实现上，扩展只有两个"加数据即可"的地方：

**① 学科目录 `config/majors.json`** —— 有限闭集。当前 13 个学科门类 / 93 个一级学科 /
502 个可匹配串（含别名、二级学科、常见方向）。**加学科只改这一个文件，不碰代码。**
> 命令 `cli.py majors`；界面「岗位管理」的专业需求输入框带 datalist 候选，
> 支持边打边选；`GET /api/majors?q=材料` 返回目录切片。

**② 领域包 `config/domains/*.json`** —— 技能按行业分包，**按需导入**。
一个包声明本行业的技能（标准名 + 别名 + 大类），导入时：合并进本体 → **备份原本体** →
报告别名迁移 → 刷新存量技能的 `skill_categories`。
> 命令 `cli.py import-domain 财务 --dry-run`（默认就是预演，不加 `--dry-run` 才落盘）；
> 界面「系统说明 → 扩展机制」同款入口；`POST /api/domains/import`。
> 内置三个包：**财务（21 条）/ 数字化（39 条）/ 检验检测（14 条）**。

为什么"按需导入"而不是一次全塞进主本体：主本体是**所有岗位共用的判定基准**，
把某个行业的词一次性全塞进去会稀释其他岗位的判定。可选包 + 备份 + 迁移报告 = **可回滚**——
导入不满意，把备份换回来即可。

> 典型案例：`成本核算` 原本只是 `成本控制` 的一个别名。转到财务岗时，本体把
> "成本核算"归一成"成本控制"，导致财务岗候选人被判「缺必需技能」。导入 `财务.json`
> 后 `成本核算` 被提升为独立条目，导入报告里显式列出 `成本控制 → 成本核算` 这条迁移。

**加一个全新岗位的完整动作**（不需要开发）：① 界面「岗位管理」新建岗位（只写岗位名），
填必需/加分技能 + 学历年限 + **专业需求**（datalist 选）；

## 十一、权限与个人信息保护

**只有 HR 一个角色**，不分子集权限、没有查看者/招聘专员/管理员之分，也没有盲筛开关——
界面是给唯一使用者用的，多一层角色只会多一层误配。

| 项 | 做法 |
|---|---|
| 联系方式 | **完整展示**（`contact_full_visible=true`）：HR 要看电话才能约面试，脱敏会让工具失去意义 |
| 存储 | 手机号/邮箱仍然 **AES-256-GCM 加密存储**，密钥来自 `config/master.key` 或环境变量 `TP_MASTER_KEY`；加密库不可用时**如实上报降级状态**，绝不假装已加密 |
| 下发边界 | 接口只下发明文手机号/邮箱，**密文、盲索引、身份键一律不下发**前端；出生年份不写入结构化档案、不参与匹配 |
| **性别（校招主场景）** | 只取简历**明写的标签行**（如 `性别：女`），**不做任何推断**、没写就留空；落库但**永不进入 `grade()`**；筛选开关**出厂关闭**，关闭时传参被忽略并如实回话（`gender_filter.applied=false`），开启时写审计 |
| 留痕 | 打开完整档案、改档、改阶段、确认提案、重复附件未落盘、**性别筛选开关切换**，全部写审计；候选人详情页返回的 `audit_snippet` 合并「档案 + 名下投递 + 涉及附件」三类记录，保密检查时可直接举证 |
| 登录 | `TP_AUTH=1` 时启用登录模式（`X-TP-Token` 会话令牌，初始口令 `change-me`，**首次登录后立即改**）；本机单机场景默认免登录，身份固定为 `hr` |

### 11.1 为什么性别做成"默认关闭的开关"

校招场景下 HR 确实需要按性别看人（比如安排宿舍、对接部门配比），所以标签要做。但它是
《就业促进法》第二十七条明确保护的属性，做法上必须给出"可核查的不滥用"：

1. **默认关闭**：设置项 `gender_filter_enabled` 出厂 `false`。开关关着时，接口即使用了
   `?gender=女` 也**不生效**，并且**如实回话**为什么（`gender_filter={enabled:false, requested:'女',
   applied:false, why:'性别筛选开关处于关闭状态（合规默认）'}`）——不静默忽略，否则会有人以为筛过了。
2. **关闭时不返回分布**：不给"顺手看一眼男女比例"这个口子。
3. **开启时留痕**：切换开关写审计（`gender_filter_enabled=False→True`），谁在什么时候开的可追溯。
4. **分布与过滤同一口径**：下拉里的数字和筛出来的人数由 `db.gender_matches()` 一个函数算，
   不会出现"显示 3 男、筛出来 2 个"这种对不上的情况。「未标注」是**可筛分组**，
   没写性别的档案不会凭空消失。
5. **绝不进评分**：`tier.grade()` 完全不读 gender。自检里有直接的反向断言——
   **同一份简历换成男/女/不填，分数与档位一模一样**（男=0.517、女=0.517、无=0.517）。

> 一句话：性别是**给 HR 看的标签**，不是**给机器用的尺子**。两者的边界在代码里是硬的。

**归档页与 CSV 两条断言的口径值得说明**（这两条最容易写成"恒通过"）：

- **归档页有没有人是使用状态，不是验收输入**：所以脚本先在归档页数勾选框，为 0 时**临时归档一位**，
  把「还有 N 天彻底删除」这条口径真正看到一遍，**验完立刻取消归档还原库状态**——
  既保证断言真的看到了东西，又不因为"今天归档页恰好是空的"而静默跳过；
- **CSV 只验"实际写进表头的列"，不验函数源码文本**：`exportCsv` 的注释里就写着
  "档位/命中/推荐理由属于系统内部判断"，那是**在解释为什么不导出它们**。
  第一版断言直接扫函数源码找"档位"，结果被自己的注释绊倒（报假失败）。
  改为用正则从源码里**提出真实的 `head` 数组**再判断，锁定的才是"导出文件长什么样"。

**「应用重算结果」的验收口径是闭环，不是看文案**：应用之后再调一次预演，
「将变化」必须归零，且应用入口必须收起。只比对弹层里写了"已更新"，
会被"界面改了、库没改"这种情况骗过去（这类"看起来做了实际没生效"的缺陷本轮就抓出过几个）。

**验收脚本先自证"验的是当前这版前端"**：单页应用整份 HTML/JS 就是一张文档，
浏览器文档缓存、后端改了前端但没重启（uvicorn 不热加载）都会让验收**静默地跑上一版代码并全绿**。
所以 `ui.py` 在页面里嵌入版本戳 `UI_BUILD`（模板哈希），`/api/meta` 回同值，
`ui_probe` 开头断言「页面 == 服务端 == 磁盘」三者一致，`goto()` 再给文档 URL 加一次性时间戳防缓存。
这四条缺一不可——#30 那轮只加了 `setCacheDisabled`，实测**管不住文档本身**（本轮 #38）。

## 十四、已知边界与后续

未做（明确留待下一阶段）：

- **学科目录的"语义兜底"仍是字面级**：`majors.json` 的方向判定当前只靠
  目录命中 + 去壳字面相似度（Dice ≥ 0.55）。真正的语义兜底（"这个专业和那个专业是不是同一族"）
  依赖向量服务，而本机向量服务仍处于**降级状态**（索引实际使用 `local-hash-v1` 哈希向量），
  因此语义相似度**未生效**——目录里没写、字面也不像的专业会如实落「无法判定」，
  这个是**保守的**（不会误判），但召回偏窄。恢复向量服务后应重测一遍学科相似度阈值；
- **领域包没有版本依赖与冲突检查**：别名冲撞（两个包把同一个别名指向不同标准名）
  按**导入顺序**决定，结果会写进导入报告的"别名迁移"里，但**不阻断导入**。
  多包叠加、或包内条目与主本体冲突时，需要人工看报告确认；也没有"包 A 依赖包 B"这类声明；
- **建议岗位（自动归岗建议）仍只看技能交集，不看专业需求**：`route-pending` 对每个在招岗位
  逐个试算，以"是否命中该岗位技能"判定建议是否可用。于是一个**专业对口但技能不在本体里**
  的候选人（实例：硕士 · 计算机技术，技能不在 `数字化工程师` 的 Java/Spring Boot/MySQL/SQL 上）
  会保持「待指定」。这是**保守的**（不硬凑），但漏掉了"专业需求本身就是一条路由线索"这个信息。
  下一阶段可把 `major_required` 纳入建议评分，作为技能之外的第二条线索；
- **本轮未重跑自检**：`cli.py selftest` 的 384 条断言上次全绿，本轮改动后未重跑
  （按交付要求跳过），下次改动前应补跑；
- **图片简历 OCR**：当前图片附件标「待人工判读」并留档，不自动识别；
- **真实 IMAP 收信**：代码就绪（只读 `SELECT` + `BODY.PEEK[]`，不删不改已读），需院内专用收件箱与凭据才能启用（界面填或 `TP_IMAP_PASSWORD`）；
- **已归档简历重新匹配到岗位**（入库/重新匹配）：本轮明确不做。来源文件只能移走/恢复，**没有"把回收目录里的文件重新入库"的入口**，也没有"把某条待指定投递改挂到某岗位"的入口；
- **保留期到期清理**：已实现**两个对象、一套 30 天保留期**——① 归档满 30 天的档案彻底删除
  （启动 + 每 24 小时守护线程，可手动触发 `POST /api/archive/purge-due` 或 `cli.py purge`）；
  ② 清空满 30 天的对话运行记录（同一套守护线程，`POST /api/agent/purge-due` 或 `cli.py purge-chats`，
  保留期内可用 `POST /api/agent/restore` 找回）。**未做**的是"按保留期自动归档"——
  即"投递满 N 年自动转入归档"仍需 HR 手动点（批量入口已备，按年归档一条命令即可）；
- **导出**：`export_external` 类工具在系统中**仍被禁用**（模型不得主动把数据外传，这条红线没动）。
  HR 手动触发的 **CSV 导出**（界面按钮，导出「个人简介 + 对应岗位」）是**人在回路**的行为，
  落地在本地文件系统、不经过模型，因此与 `export_external` 禁令不冲突。

## 十五、合规

简历属个人敏感信息：本地部署、数据不出内网、按保留期限留存、不调用公网 API。
系统只建议不决定，不淘汰任何简历、不自动对外发送任何消息；
岗位只有停用（不删除）、来源文件只移入回收目录（可恢复）。

**关于"彻底删除"的边界**（v1.5 需明确说明，避免与"不物理删除"混淆）：

1. **没有随手删除的入口**。候选人档案的删除**必须**先归档、**再等满 30 天**，
   未满 30 天点删除会被 **409 明确拒绝**并告知剩余天数。这个顺序在接口层是强制的；
2. **30 天是冷静期，不是流程形式**。窗口期内「取消归档」随时可恢复，误操作可逆；
3. **删除的是档案正文，留的是行为记录**。到期清理写 `purge` 审计（谁、何时、依据什么规则清了谁），
   原件移入回收目录 `REMOVED_DIR/purged` 而非直接抹除，为合规核查保留凭据；
4. **导出的 CSV 只含"个人简介 + 对应岗位"**，不含档位、命中技能、推荐理由等内部评分口径——
   评分口径留在系统内（界面 + 审计），不随文件流出。

**性别**按《就业促进法》第二十七条（禁止就业性别歧视）处理：只取简历明写的标签、不做推断、
筛选开关出厂关闭、开启留痕、**任何情况下不参与评分与分级**。开关放在「系统说明」页并附带上述依据，
任何人打开这一页都能看到它为什么这样设计。

## 0. 一句话定位

把"一次性的简历筛选工具"升级为**院内私有的人才资产底座 + 可对话的人才智能体**：
所有进院简历**一档不丢**、按能力建档、能被任意新岗位随时召回、全过程可审计。

三个层次的价值递进：

| 层次 | 目标 | 交付感 |
|---|---|---|
| 第一层：**不丢** | 简历集中收拢、原件留档、零重复 | HR 不用再翻邮箱 |
| 第二层：**找得到** | 结构化建档、技能归一、语义检索 | 一句话查出"做过 X 的人" |
| 第三层：**用得好** | 分级推荐、主动召回、流程度量 | 人才资产可盘点、可激活 |

## 1. 为什么是"人才库"而不是"筛选器"

### 1.1 现状问题诊断

| 现状 | 直接后果 |
|---|---|
| 每次招聘从零收简历 | 半年前投递但当时不匹配的人，永久流失 |
| 简历散落在个人邮箱 / 微信 / 纸质 | 无法检索、无法统计、人员变动即断档 |
| 筛选是一次性判断 | 同一个人换个岗位可能很合适，判了就没了 |
| 无技能词表、无标签 | "会做真空熔铸的人有哪些"这类问题无法回答 |
| 无审计、无权限 | 涉密场景下不合规，简历谁看过不可查 |

### 1.2 大厂做法（值得借鉴的四点）

1. **一档多投（Candidate / Application 分离）**
   人（Candidate）与投递（Application）是两张表。一个人只有一份档案，投递可以有 N 次。
   "2023 年投 A 岗未成、2026 年投 B 岗"是同一个人的两条记录，历史评价可继承。

2. **人才库激活（Talent Pool Activation）**
   当期不匹配但优秀的人进池，新岗位开放时**主动召回**，而不是重新发招聘广告。

3. **技能本体 + 标签体系**
   不做纯全文检索，而是"技能词表 + 岗位族 + 能力等级"。
   同一技能的不同写法归一到同一 ID（`XRD` = `X射线衍射` = `X-ray diffraction`）。

4. **ATS 与人才库分离**
   ATS 管流程（Pipeline 状态机），人才库管资产（长期沉淀）。两者通过 Candidate ID 关联。
   研究院场景 ATS 能力偏弱，人才库反而更该先建——**流程可以后补，资产丢了补不回来**。

### 1.3 明确不做的事（红线，写死在设计里）

1. **不自动淘汰、不自动发拒信、不自动对外发送任何内容**；
2. **不做录用决定**，只做分级建议 + 证据罗列；
3. **数据不出内网**，简历正文不发给任何公网模型；
4. **不物理删除简历**（除保留期到期或候选人主动要求删除）。来源文件可以移走，但**移入回收目录、可恢复**，不是抹掉；
5. **不抽取敏感属性**（民族 / 婚育 / 宗教 / 健康 / 年龄/ 出生年份），岗位有法定要求除外。
   **性别是唯一例外，且边界写死**：只取简历**明写的标签行**（不推断、不猜测），
   筛选开关**出厂关闭**，开启与关闭都留审计，**任何情况下不进入评分函数**（详见 §12.2c 第 3 条）。

## 2. 设计原则（五条，贯穿全局）

| 原则 | 落地方式 |
|---|---|
| **不丢** | 解析失败也入库，标"待人工判读"；原件进归档区，只增不改 |
| **建议与决定分离** | `tier_suggested`（系统）/ `tier_final`（HR 确认），字段级隔离；**JD 改后重算也不覆盖已确认档位**（v1.4）；界面无档案删除入口 |
| **可溯源** | 每条结论带证据（命中什么、缺什么、原文片段）；每次变更落审计（含重算的变更前后、性别开关的切换） |
| **最小权限 + 完整可用** | **单一 HR 角色**，不分子集权限（v1.1→v1.2 从三角色收拢：系统只有唯一使用者，多角色带来的是配置风险而非收益）；联系方式**完整展示**（脱敏会让"约面试"做不成），但密文/盲索引/身份键不下发前端；导出必留痕 |
| **模型可换** | 规则层与模型层解耦；无模型时功能完整（降级不失效），换模型不改业务代码 |

## 3. 整体架构（六层）

| 层 | 职责 | 当前选型 | P0 状态 |
|---|---|---|---|
| **L6 交互层** | HR 工作台、对话面板、导出预览 | 单页 Web（原生 JS + FastAPI 静态） | 已完成 |
| **L5 智能体层** | 提问 → 选工具 → 执行 → 回灌 → 答复 | 自研 ReAct 最小循环（4 轮上限） | 骨架完成 |
| **L4 编排层** | 收信 → 解析 → 抽取 → 分级 → 入库（确定性流程） | Python 管道，逐步可重放 | 已完成（除收信） |
| **L3 能力层** | 模型服务、向量检索、OCR、文件解析 | Ollama / vLLM / DeepSeek，可切换 | 接口就绪，模型待接 |
| **L2 数据层** | 候选人 / 投递 / 附件 / 技能 / 标签 / 审计 | SQLite（→ PostgreSQL + pgvector） | SQLite 已完成 |
| **L1 基础设施** | 内网主机、GPU、备份、凭据管理 | 单机 → 部门 GPU 机 → 院级 | 单机 |

**数据流**：

```
邮箱 → 收信台账 → 附件归档(原件) → 解析 → 抽取 → 技能归一 → 建档
   → 分级(建议) → HR 人审(决定) → 入库 → 检索/召回/分析 → 审计
```

## 4. 数据模型设计（核心）

### 4.1 实体关系（文字表述）

```
Candidate (人) 1 ── N Application (投递) N ── 1 Job (岗位)
Candidate      1 ── N Document (附件/原件)
Candidate      N ── N Skill (经 candidate_skills，带等级与证据)
Candidate      N ── N Tag
Application    1 ── N AuditLog / AgentRun
```

### 4.2 表设计

**candidates（人，一档）**

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `identity_key` | 去重主键（见 4.3） |
| `name` | 基础信息（**出生年份不采集、不入库、不参与匹配**；无联系方式时才参与弱身份键） |
| `gender` | 校招场景的展示标签（v1.4 新增）：只取简历**明写**的 `性别：X`，取不到就留空（`''`/`NULL`），**绝不推断**；**不参与 `grade()` 评分**，也不参与身份键 |
| `phone_enc / email_enc` | 加密存储（AES-GCM） |
| `edu_level / school / major` | 最高学历口径 |
| `years_exp / current_org` | 经验与现单位 |
| `source_first / first_seen_at / last_active_at` | 首次来源、首次入库、最近活跃 |
| `pool_status` | `在池 / 已联系 / 面试中 / 已入职 / 已归档` |
| `pii_level` | `普通 / 敏感 / 涉密`，驱动访问隔离 |
| `merged_into` | 被合并指向，**不做物理删除** |

**applications（投递，N 次）**

| 字段 | 说明 |
|---|---|
| `id / candidate_id / job_id` | 关联 |
| `channel` | 邮箱 / 内推 / 招聘会 / 官网 |
| `applied_at / resume_doc_id` | 投递时间与当次简历版本 |
| `score / tier_suggested / tier_final` | 评级（建议 / 决定分离） |
| `stage` | `新投递 / 已联系 / 初面 / 复面 / 待offer / 已入职 / 已结束` |
| `reasons / risks / hits / miss` | 归因证据（含原文片段引用） |
| `extract_mode / confidence` | 抽取通道与置信度 |
| `needs_review` | "待人工判读"标记 |

**documents（原件与解析分离）**

| 字段 | 说明 |
|---|---|
| `file_hash` | 全局唯一（SHA256）→ 幂等去重 |
| `file_path / mime / size` | 原件位置，**只增不改** |
| `source_message_id` | 溯源到邮件 |
| `raw_text / text_len` | 解析文本（可重跑，原件不动） |
| `parse_engine / parse_ok` | PyMuPDF / MarkItDown / OCR / 失败 |

**skills / candidate_skills（技能本体）**

| 表 | 字段 |
|---|---|
| `skills` | `id / canonical_name / aliases(JSON) / category（材料·工艺·表征·软件·管理）/ parent_id` |
| `candidate_skills` | `candidate_id / skill_id / level（了解·熟练·精通）/ evidence（原文片段）/ from_doc_id` |

**tags / candidate_tags（标签体系）**

| 类别 | 示例 |
|---|---|
| 来源标签 | 校招 / 社招 / 内推 / 招聘会 |
| 状态标签 | 在读 / 在职 / 离职 / 应届 |
| 类型标签 | 博士 / 海归 / 退役 / 涉密相关 |
| 能力标签 | 真空熔铸 / 钛合金锻造 / 金相分析 |

**jobs（岗位尺子）**：`jd_json`（must / preferred）、`owner`、`status`、`opened_at / closed_at`

**email_messages（收信台账）**：`message_id(唯一) / uid / from / subject / received_at / attachment_count / processed / error`
→ 每一封都留痕，失败可重放。

**audit_log（审计）**：`entity / entity_id / action / before / after / operator / ip / ts`

**agent_runs（智能体可观测）**：`session_id / question / tool_calls(JSON) / model / tokens_in / tokens_out / latency_ms / status / answer`
→ 可算成本、可复盘工具链、可发现异常提问。

### 4.3 四个关键设计决策

**决策一：一档多投**
简历不再是"一个人"的全部，而是一次投递的附件。人才库沉淀的是**人 + 能力档案**，与具体岗位解耦。
价值：新岗位开放时，不需要重新收简历，直接从库内召回历史投递者。

**决策二：身份合并用"弱规则 + 人工确认"，不自动合并**
`identity_key` 生成优先级：`手机号 → 邮箱 → (姓名 + 出生年月 + 毕业院校)`。
命中不同 key 但相似度高（如手机号相同、姓名不同）时，系统只**提示"疑似重复"**，由 HR 决定是否合并。
理由：自动合并一旦误判，会把两个人的档案混在一起，破坏性远大于重复入库。
合并采用**软合并**（`merged_into` 指向主档），随时可拆。

**决策三：原件与解析分离**
原件永远保留，解析结果可重跑。换更好的解析器 / OCR / 模型后，可对历史简历**批量重抽**，不需要重新收简历。
这是长期资产化的前提。

**决策四：评分尺子可改，但"重算"必须可预演、可追溯、不覆盖人的结论**（v1.4 新增）
岗位 JD 是会变的（换个方向、加个门槛），改了之后已有投递要不要跟着重算？答案是**要，但由 HR 决定**：

- **先预演、后应用**：`apply=false` 只算差异、一个字不写库；HR 看过"谁从 B 变 D、为什么"再点应用。
- **不覆盖 HR 已确认的档位**：`tier_final` 已定或状态「已确认」的只记差异、不改数据——
  "系统只建议不决定"这条不变式，在追溯场景同样成立。
- **重算必须可重复**：只走规则通道、不调模型，且**画像从 `documents.raw_text` 重跑**而不是读库
  （`certificates` / `skill_detail` 等字段并未落库，读库会把分数算低，看起来像"改 JD 降档"其实是画像读残）。
- **算不出来的如实说**：简历原文缺失（扫描件解析失败）的投递标「无法重算」，**分数保持原值不清零**。

这是"原件与解析分离"（决策三）在评分维度上的自然延伸：**尺子与画像都可以更新，唯独不能悄悄改掉人的判断。**

## 5. 智能体能力规划

### 5.1 "工作流"与"智能体"的边界

| 环节 | 谁做 | 为什么 |
|---|---|---|
| 收信、去重、解析、建表、落审计 | **工作流**（确定性） | 规则明确、结果可预测、零模型成本 |
| 结构化抽取、匹配归因、技能归一、标签生成、提纲生成、语义召回 | **智能体 / 小模型** | 需要理解与判断，规则写不完 |
| 定档、淘汰、联系候选人、发任何对外内容 | **人** | 有法律与人事后果，系统不得越权 |

一句话：**能写死的绝不交给模型，要判断的才交给模型，有后果的必须交给人。**

### 5.2 工具集设计（智能体的"手"）

按风险分级，权限不同：

| 类别 | 工具 | 风险 | 权限策略 |
|---|---|---|---|
| **读** | `search_candidates` / `get_candidate` / `candidate_stats` / `search_by_skill` / `pipeline_overview` / `mailbox_status` | 低 | 默认开放 |
| **算** | `analyze_fit` / `compare_candidates` / `draft_interview_questions` / `suggest_tags` / `match_jobs` / `summarize_pool` | 低（只读+生成文本） | 默认开放 |
| **写（需确认）** | `create_tag` / `update_stage` / `merge_candidates` / `add_note` | 中 | 模型只输出**待确认操作**，HR 点确认才落库 |
| **外发** | `send_email` / `export_external` | 高 | **不提供**；导出走人工 + 审计留痕 |

**P0 已实现 6 个**：`search_candidates`、`get_candidate`、`candidate_stats`、`analyze_fit`、`draft_interview_questions`、`mailbox_status`。

### 5.3 小模型能做什么、不能做什么（本场景核心结论）

**能做到的 7 类事**（全部是"短上下文 + 结构化输出"任务，7B–14B 甜点区）：

| # | 能力 | 说明 | 建议规格 |
|---|---|---|---|
| 1 | **结构化抽取** | 自由格式简历 → JSON（姓名/学历/年限/技能/项目） | 7B 起，14B 更稳 |
| 2 | **岗位匹配归因** | 不只给分数，给"命中 3 项必需技能、缺真空熔铸、有 2 项加分"+ 原文引用 | 14B |
| 3 | **技能归一** | 同义/近义技能映射到本体 ID | 3B–7B |
| 4 | **标签生成** | 从简历文本生成候选标签，人审后入库 | 7B |
| 5 | **相似人才召回** | "库里最像的 5 个人"——用 **embedding + 向量检索**，不用 LLM 逐个读 | 0.1B–0.6B |
| 6 | **生成类文书** | 面试提纲、一页纸画像、内推摘要 | 14B |
| 7 | **库级问答** | 自然语言问库（"今年硕士以上做过钛合金、没联系过的有几个"）→ 转成工具调用 / 结构化查询 | 14B，长尾走大模型 |

**不能做 / 不该给的**（边界）：

- ❌ **不能定档**——只能给建议 + 证据；
- ❌ **不能做录用判断**；
- ❌ **不能凭简历推断敏感属性**（民族/婚育/宗教/健康）——抽取口径中明确剔除，这是 PIPL 与反歧视的硬要求；
- ❌ **不能取代面试**；
- ❌ **不能无证据"生成"技能**——抽取必须带 `evidence` 原文片段，无片段不算命中（这是防幻觉的硬约束）。

### 5.4 模型分层策略（成本与能力的甜点区）

| 任务层 | 推荐规格 | 代表模型 | 理由 |
|---|---|---|---|
| 分类 / 判空 / 去重相似度 | 1B–3B | Qwen2.5-1.5B / 3B | 任务极简单，可 CPU 跑，成本最敏感 |
| 抽取 / 标签 / 归因 / 提纲 | 7B–14B | Qwen2.5-14B / GLM-4-9B | **甜点区**；纯文本、短上下文 |
| 库级复杂问答 / 跨文档推理 | 大模型兜底 | DeepSeek / 内网 32B+ | 调用频率低，值得多花 |

**关键洞察**：人才库场景中 **约 90% 的调用量不是"生成"，而是"抽取"和"检索"**。
抽取用 7B、检索用 embedding（亚 B 级），只有长尾问答才落到大模型——这就是小模型在本场景**够用**的根本原因。

**成本估算（按 1000 份简历为一批）**

| 方案 | 边际成本 | 前提 |
|---|---|---|
| 全用公网大模型 | 约 400 万 token 级（1000 份 × 约 4k token） | 有网络、有费用、**简历出内网（涉密不可接受）** |
| 全本地小模型 | ≈ 0（仅电费） | 需一台 GPU 机器 |
| **混合（推荐）** | 本地抽取 + 少量大模型问答，成本下降约一个数量级 | 抽取内网、问答可内网或按密级分流 |

**提示词缓存**：系统提示 + 岗位尺子在所有调用中不变，把不变部分前置可命中缓存，
重复调用的输入 token 成本约降一个数量级（DeepSeek / Anthropic 等均支持）。**批量跑简历时应显式开启。**

### 5.5 智能体运行时治理

| 机制 | 作用 |
|---|---|
| 最大工具轮数（当前 4 轮） | 防死循环、防费用失控 |
| 无模型优雅降级 | 模型不可用时回落到规则模式，界面照常可用 |
| `agent_runs` 全量记录 | token / 耗时 / 工具链可复盘，可核算成本 |
| 写入类工具"先提案后执行" | 模型不能直接改数据 |
| 只读工具默认开放 | 降低使用门槛，鼓励 HR 多问 |

### 5.6 交互示例（让它"像智能体"）

| HR 问法 | 期望工具链 | 期望回答 |
|---|---|---|
| "库里有没有做过真空熔铸、会 XRD、近一年投过的人？" | `search_by_skill(真空熔铸)` → `search_by_skill(XRD)` → 交集 → 时间过滤 | 3 人（附档位、最近联系时间）+「是否群发通知」的**待确认操作**（默认不执行） |
| "12 号不适合工艺岗，那适合研发岗吗？" | `get_candidate` → `match_jobs` → 排序 | 匹配度排序 + 理由 + 差距项 |
| "本月新收多少简历？各档多少？哪些还没人看？" | `candidate_stats` → 挂起清单 | 数字 + 待办清单 |
| "给我 5 个和 12 号最像的人" | 取 12 号向量 → 向量检索 | 相似人才卡片（含相似维度解释） |
| "这个人面试该问什么？" | `get_candidate` → `draft_interview_questions` | 8–10 题，按能力缺口定制，附追问点 |

## 6. 邮箱接入方案（P1）

### 6.1 链路

```
专用招聘收件箱 → IMAP 只读(993/SSL) → 游标增量拉取 → 附件提取
   → 原件归档(只增不改) → 解析 → 抽取 → 入库 → 待 HR 确认
```

### 6.2 三层去重（保证"零重复"）

| 层 | 去重键 | 解决的问题 |
|---|---|---|
| 邮件层 | `message_id` | 同一封邮件重复拉取 |
| 文件层 | `SHA256(附件)` | 同一份简历不同文件名 |
| 内容层 | `identity_key`（姓名+手机+院校） | 同一个人不同版本简历 |

### 6.3 "不丢"的三道保险

1. 附件**先落盘归档**，再做解析——解析崩了原件也在；
2. 解析失败 → 建"待人工判读"记录，**仍可被搜到**，HR 看原件；
3. 收信台账逐封记录处理结果与错误，支持重放。

### 6.4 安全约束

- 只读账号：**不删信、不改已读、不打标签**；
- 凭据走环境变量 / 密钥文件，不进代码、不进日志；
- 内网邮箱；简历正文不发送给任何公网服务；
- 附件类型白名单 + **大小上限**（`max_attachment_mb`，默认 20MB。**邮件与文件夹导入共用这一把尺子**——v1.3 时大小上限只在邮件路径生效，文件夹导入能把一本 17MB 的书放进来，见 §12.2c 第 5 条）；
- 接入院内病毒扫描（可选）。

### 6.5 配置体验：让 HR 自己就能配通

"配不上"通常不是权限问题，而是**信息不对称**——填什么服务器、用密码还是授权码、为什么点了收取没反应。
所以把这三点做进界面，而不是写进文档：

| 措施 | 解决的问题 |
|---|---|
| **服务商预设** `GET /api/mailbox/presets`（腾讯企业邮 / QQ / 163 / 阿里云企业邮 / Outlook / Gmail） | 服务器与端口不用查文档；**端口填错是"测试连接永远失败"的头号原因** |
| **保存即提醒**（`_mailbox_warnings()` 一处产出，保存/测试/读取三接口共用） | 模式还是 `eml`（读本地目录）却填了 IMAP 账号 → 点"收取简历"当然毫无动静，因为**它压根没连邮箱**。这类提醒必须由界面直说 |
| **点名授权码** | 国内邮箱（QQ/163/企业邮）**必须用授权码**，登录密码一律失败；含糊说"缺少凭据"等于没说 |
| **测试连接给出下一步** | 失败时不止报错，还给下一步该改哪一项；成功时说明连的是哪个账号 |

> 提醒**只在一处产出**、界面直接显示后端返回的内容，界面不再自己复写一套规则——
> 否则后端加了提示、界面还是旧的，同一条规则会有两个说法。

## 7. 合规与数据治理（研究院场景强化）

| 项 | 措施 |
|---|---|
| 法律依据 | 《个人信息保护法》：最小必要、告知同意、目的限定、保存期限；**性别按《就业促进法》第二十七条（禁止就业性别歧视）单独约束**，见下 |
| PII 落地 | 手机/邮箱/证件号加密存储（AES-GCM，密钥独立管理）；界面**完整展示**（单 HR 角色，不做按角色脱敏——脱敏会让"要约面试"这件事做不成）；**密文、盲索引、身份键一律不下发前端** |
| 反歧视 | 抽取口径剔除民族/婚育/宗教/健康/年龄/出生年份；**性别**只取简历明写标签、默认关闭筛选开关、开启与关闭都留审计、**永不进入 `grade()`**；不做"综合画像评分" |
| 性别处理边界 | ① 不推断（没写就留空）；② 开关出厂关闭，关闭时传参被忽略**并如实回话**；③ 关闭时不返回性别分布；④ 开启/关闭写审计；⑤ 分布与过滤同一口径；⑥ **同一份简历换性别，分数与档位完全一致**（自检 S-c 有反向断言）。开关放在「系统说明」页并附上述依据 |
| 权限 | **单一 HR 角色**，不分子集权限（v1.1→v1.2 已从三角色收拢，见 §12.1）；导出类工具在工具层禁用 |
| 审计 | 谁何时看了谁的简历、改了什么档、确认了什么提案、**何时切换了性别开关**，全量留痕，可导出接受检查 |
| 保留期 | 未录用简历默认 12–24 个月（按院内制度定），到期提醒 + 可配置清理；候选人可要求删除 |
| 涉密隔离 | 涉密岗位/人员单独标记（`pii_level`）与访问隔离，不与其他岗位混池 |
| 信创适配 | OS：麒麟/统信；DB：达梦/人大金仓（或 PostgreSQL 信创版）；芯片：海光/鲲鹏/昇腾 |

## 11. 下一步建议（三选一）

| 选项 | 内容 | 交付速度 | 价值感 |
|---|---|---|---|
| **A** | 先接邮箱（P1）：把简历真正收进来 | 快 | 立即可见（不再翻邮箱） |

**推荐路径**：A + B 的**最小闭环**——P1 中只做"收信 + 一档一投 + 自然语言查询"，暂不做技能本体。
理由：价值体现有其顺序，**先不丢（A），再找得到（B），最后才是管理（P3 管道/BI）**。
本体与标签（P2 完整版）应在有真实数据量（≥300 份）之后再投入，否则词表覆盖不全、归一规则靠猜。

## 12. 实现与验证状态（2026-09-22）

> 本节记录"方案 → 代码"的落地情况，避免文档与实现各自表述。

### 12.1 本轮口径调整（v1 → v2，来自试用反馈）

| 变更 | 原口径 | 现口径 | 理由 |
|---|---|---|---|
| **角色** | 三角色 RBAC（查看者/招聘 HR/管理员）+ 按角色脱敏 + 盲筛开关 | **单一 HR 角色**，不分子集权限、不做按角色脱敏、去掉盲筛 | 系统只有唯一使用者；多角色带来的是配置风险而非收益。**手机/邮箱仍加密存储，密文与盲索引不下发前端**——安全边界不降 |
| **部门与岗位** | 只有一个全局岗位，CLI/界面无法增删 | 界面「部门与岗位」可**新增部门、在部门下新增岗位**；**只能停用/启用，不能删除** | 一个收件箱收多个岗位的简历；岗位下已有投递时删除会让历史无法解释 |
| **邮箱凭据** | 只能靠环境变量 `TP_IMAP_PASSWORD` / 手改 `config/mailbox.json` | 界面「邮箱配置」填写 IMAP 全部参数 + 「测试连接」；口令写入 `config/imap.secret`（`0600`，不入版本库，不回显） | 让 HR 自己能配，不必找人改服务器；口令不落在 UI、日志、版本库里 |
| **收信归岗** | 收取时统一挂到当前唯一岗位 | **按邮件标题归岗**：标题里出现在招岗位名 → 归该岗位并用该岗位的 JD 评分；否则落「所属岗位待指定」 | 反馈原话是"邮件标题会带上投递岗位的"；标题是唯一可靠的岗位信号 |
| **上传归岗** | 文件夹导入也挂岗位 | **文件夹上传一律不归岗**，只做解析/分级/建档，由 HR 事后指定 | 文件夹往往是混合批次，按标题猜岗位比留空更糟 |
| **收信台账页** | 界面上有一页独立的收信台账 | 去掉该页 | 台账不是 HR 的日常动作；数据仍在库里，详情页与审计里可查，不需要单独一页 |
| **界面字号** | 基础 13px | 基础 15px，标题与卡片间距同步放大 | 反馈"字体太小" |

补充两条与上面配套的规则：

- **部门停用 → 其下岗位一并停止归岗**：否则会出现"部门已经关了，简历还在往这个部门的岗位上挂"；
- **停用是软删**：`active=0` + 状态置「停用」，岗位/部门行仍在，历史投递的 `job_id` 一直有效，随时可恢复。

一个人不该因为系统里只有材料类尺子，就被判成"材料类不匹配"。

### 12.2h 追加变更（2026-09-23：清空纳入 30 天保留期，来自第四轮试用反馈续）

用户原话：**"删除三十天之后自动清理吧，30 天之内可以恢复"**。

这句话把上一轮遗留的一个悬而未决的问题一并回答了。上一轮实现的是"清空 = 只推进清空点、
不物理删除"，当时的理由是 `agent_runs` 同时承担 token 成本核算与治理审计，
立刻删掉等于把"花了多少、系统做了什么"一起抹了。但那个版本**没有给出到期时间**——
即"这批记录到底会不会被清掉、什么时候清掉"是悬空的一句话。
本轮按用户口径补齐，并明确**与档案"归档满 30 天彻底删除"共用同一个 `PURGE_AFTER_DAYS`**：

| # | 反馈原话（要点） | 落地做法 | 关键设计取舍 | 验证 |
|---|---|---|---|---|
| 1 | "删除三十天之后自动清理吧，30 天之内可以恢复"（范围经确认：**对话清空也纳入同一规则**） | ① `db.clear_chat()` 改为**软清空**：推进清空点到 `MAX(agent_runs.id)` + 写 `chat_purge_after`（`now + PURGE_AFTER_DAYS`）+ 审计写明到期日；② 新增 `db.chat_clear_state()`（清空点/清空时间/到期时间/还剩几天/能否恢复）与 `db.restore_chat()`（清空点三键复位 + `chat_restore` 审计）；③ 新增 `db.purge_due_chats()`：**先汇总再删明细**，到期才删 `id <= 清空点` 的运行记录；④ 接口 `POST /api/agent/restore`、`POST /api/agent/purge-due`；⑤ 后台任务 `_startup_purge_task` 在原有归档清理旁并列接入对话清理（启动一次 + 每 24 小时）；⑥ 界面加「恢复对话」按钮与保留期提示条；⑦ `cli.py purge-chats` 与 `purge` 对称；⑧ 历史接口新增 `purge_after` / `retention_days` / `days_left` / `restorable` 字段 | ① **只允许一个"缓冲期"数字**：两个功能各写一个 30 迟早会漂移，所以共用 `PURGE_AFTER_DAYS`；② **`restorable` 只看清空点在不在，不卡到期时间**：后台任务每 24 小时才跑一次，到期与真正删除之间有最多 24 小时窗口，这段时间记录仍在库里——**系统还没删的，人就该能捞回来**，宁可让人多救一次也不抢在人前面做不可逆决定；③ **多次清空以最后一次为准**：整批一起在最后一次清空后 30 天清理，方向是"保留更久"，不提前删；④ **删明细前先写汇总**：条数/token 合计/运行号与时间区间进 `chat_purge` 审计，逐条明细可删、总量证据不删；⑤ **审计三条痕迹永久保留**（`chat_clear` / `chat_restore` / `chat_purge`）——"谁什么时候清空、又什么时候恢复、系统什么时候清掉"是一个完整行为链，缺一半就说不清；⑥ **没有可解析的到期时间就永不动手**：宁可永不自动删，也不因脏数据误删；⑦ **清空文案与提示条如实写出到期日**，不假装没有这条线 | 自检「S续」新增 10 条（清空返回保留期口径 / 刚清空倒计时为完整 30 天 / 历史接口如实汇报 / **保留期内清理明确拒绝且库内条数前后一致** / 恢复后全部运行重新可见 / 恢复后无到期时间 / 恢复留痕 / 到期真的删记录 / **汇总先进审计** / 清理后清空点复位）；实机脚本 `tools/verify_chat_history.py` 扩到 **14 项断言**全通过（清空返回到期时间与 `days_left=30`、库内运行记录一条不少、保留期内 `purge-due` 回"未到期"、恢复后全部问答重新可见且不再有到期时间）；界面验收新增「软清空落点」断言并落盘截图 20b/20 |

**这轮暴露的两个缺陷都是"字段改名改一半"**（见 §12.4 #52/#53）：`chat_clear_state()` 的返回键
统一为 `cleared_through_run` 后，`_chat_since()` 与 `restore_chat()` 里各剩一处旧键名 `through_run`——
两处都是**读字典键**，一旦执行就抛 `KeyError`。`_chat_since()` 那处更严重：
它被**每一次历史读取**调用，等于 `/api/agent/history` 与清空计数全线不可用。
这类错误的特征是**不会在语法检查、也不会在"只测了另一条分支"的自检里暴露**，
只有真的把路径走一遍（或在断言里覆盖到）才会炸。教训：**重命名返回键之后，
要顺着"谁在读这个键"数一遍**——与 #46 同一种病（一处口径、多处消费）。

| 54 | **保留期倒计时向下取整，清空当天就显示"还剩 29 天"**：`days_left = int((due - now).total_seconds() // 86400)`，而 `due = now + 30 天` | 清空是"上一秒写 `due`、下一秒算倒计时"，30 天整减去毫秒级执行耗时再向下取整 = **29**。用户看到"刚清空就只剩 29 天"，读起来像系统偷偷少给了一天；更要紧的是**与归档页的口径不一致**（归档用 `days - (now - ts).days`，当天显示 30 天），同一个产品里两个"还剩几天"给出不同答案 | 改为向上取整（`-(-secs // 86400)`），与归档 `days - elapsed.days` 同一口径：刚清空显示"还剩 30 天"。教训：**倒计时的取整方向是产品决定，不是数学细节**——凡是给人看的"还剩 N 天"，都要先确认边界当天显示几 |
| 55 | **「运行环境」把降级显示成正常，且看不出模型走的是公网还是内网**：`ui.py` 的向量模型行只渲染 `model · dim 维 · 已索引 N 人`，**不渲染 `search.reachable` 与 `search.error`**；对话模型行只给模型名，**不给 `base_url`** | 两处都实际误导：① 本机 Ollama 没起时，向量通道已退回 `local-hash-v1` 哈希兜底（检索质量下降），但界面显示"embeddinggemma:latest · 384 维 · 已索引 7 人"——**384 维是兜底向量的维度，读起来却像配置的模型工作正常**；② 对话模型只显示 `qwen3-14b`，看不出它其实连的是**公网百炼**（`dashscope.aliyuncs.com`）而不是内网 vLLM——而这恰恰是信创合规评审第一眼要看的信息。与 v1.6 反复强调的"降级要如实上报"直接冲突 | ① 对话模型行补 `base_url`；② 向量模型行补"服务可达 / **服务不可达（降级中）**"与 `error` 详情；③ **当 `index_model` 与配置的 `model` 不一致时，界面显式点出"索引实际使用 X ——配置的向量模型没连上时自动退回本地哈希向量，检索质量会下降"**（配置是谁、实际用的是谁，两个都要说）。并把这套口径写成界面断言（`ui_probe` ⑦e），断言"可达状态与接口一致""base_url 在页面上""降级时点出实际使用的索引模型"——**光改文案会在下次重构里悄悄回退，只有断言能锁住** |

> v1.6 的教训：#46 与 #47 其实是一件事的两面——**系统里有不止一处在"读同一份东西"**。
> #46 是三处在读尺子，#47 是两处在读技能，#50 是两处在读技能（一处挂载、一处过滤）。
> 只要同一个概念被两处以上实现，改口径时就必然会漏掉其中一处，而漏掉的那一处
> **不会报错，只会给出一个看起来合理的错答案**。所以本轮的修法统一是：
> 把口径收敛到一个函数（`resolve_candidate_job` / `_skill_names` / `_attach_skills` 前置），
> 让"漏改"在结构上不可能发生。
> #49 则是另一种典型：**断言写不出来的时候，往往是产品真的有问题**——
> 当时第一反应是"我的断言写错了"，改断言会让它变绿，但同秒操作的歧义仍然存在。
> #52/#53 是 #46 的镜像：**这次不是"读同一份东西的多处实现"，而是"同一个键名的多处消费"**——
> 前者改口径会漏，后者改字段名会漏，两者都靠"顺着一路数一遍"来防。
> #54 则提醒：**边界当天的显示值要专门想一遍**，取整方向、时区、跨零点都是同一类问题。
> #55 是另一种："**接口说全了、界面没说全**"——`/api/meta` 本来就把 `reachable`、`error`、
> `index_model` 都返回了，是界面选择不渲染。它是本产品反复出现的一类缺陷的变体：
> **系统知道自己处于降级，但没有把这件事告诉人**。判据很简单——
> 凡是"系统内部有两种运行态（正常/降级）"的地方，界面上都必须能看出当前是哪一种。

### 12.5 尚未落地

**已知架构性缺口：岗位 / 领域的扩展性**——新增岗位需先扩本体，且未收录项会被剔除出方向判定
（实测财务岗 9 项需求仅 1 项收录却判"对口"、数字化岗判"无法判定"）。
诊断与改造方案见 **§13**，**已于 2026-09-23 实施完毕（v1.7），实施记录见 §13.7**。
图片简历 OCR；真实 IMAP 收信（需院内专用收件箱与凭据，界面已可配置）；
**导出外网**（`export_external` 类工具在模型工具层仍禁用，需按院内流程单独开放并留痕；
HR 手动触发的本地 CSV 导出已可用，见 §12.2f 第 3 条）。
**保留期到期清理**：已实现两个对象共用一套 `PURGE_AFTER_DAYS` 保留期——① "归档满 30 天彻底删除"；
② **"清空满 30 天自动清理对话运行记录"**（保留期内可 `POST /api/agent/restore` 恢复，
见 §12.2h）。两者都由启动任务 + 24 小时守护线程驱动，并各有手动触发入口。
未做的是"投递满 N 年**自动转入归档**"——批量入口已备（按年归档一条命令），但触发仍需 HR 手动点，
不做全自动归档的理由是：**归档是人对"这批数据还要不要出现在日常视图里"的判断，不该由系统替人决定**。

**明确不做**（本轮已确认，写进设计以免反复讨论）：

- **已归档简历的「重新匹配」**：本次只做"按岗位 JD 重算已有投递"（同一批投递、换尺子），
  **不做"把回收目录里的文件重新入库"**，也不做"把某条「所属岗位待指定」的投递改挂到某岗位"。
  数据结构支持（`applications.job_id` 可改），但界面不开口子——归岗口径是全局唯一的，
  再开一个人工改挂入口会破坏"标题归岗 + 逐岗位轮询"这条口径的可解释性。
- **候选人档案的直接删除**：只有来源文件可以移入回收目录。档案的彻底删除**必须先归档、
  再等满 30 天**（接口层强制，未到期返回 409），**没有"点一下立刻删掉"的入口**——
  历史投递必须留得住。满 30 天的清理仍写 `purge` 审计并把原件移入 `REMOVED_DIR/purged`，
  删的是档案正文、留的是行为记录。

## 13. 岗位 / 领域扩展性：从"封闭词表"到"开放匹配"

> 触发问题（2026-09-23）：**新增岗位要一直扩本体吗？换成财务岗位怎么办？能不能干脆都交给模型打分？**
> 本节给出实测证据、根因诊断、三条不变式与落地步骤。**已于 2026-09-23 实施，见 §13.7。**

### 13.1 实测：新领域一进来，判定就失真

用当前代码实测（同一份候选人、只换 JD）：

| 场景 | 需求项在本体的命中率 | `grade` 分数 | 风险提示 | `major_match` 判定 |
|---|---|---|---|---|
| 科学研究岗（专业需求原样填入必需技能） | 1/6 | **0.538** | 报 5 项"缺必需技能" | 对口（依据仅剩 1 项） |
| 科学研究岗（专业需求翻译为技能） | 4/4 | **0.89** | 无 | — |
| 数字化工程师岗 | 0/5 | — | — | **无法判定** |
| **财务岗**（会计核算/财务报表/税务申报/成本核算/资金管理/预算管理/财务分析/用友/金蝶） | **1/9** | 0.656 | 报 5 项"缺必需技能" | **对口** |
| 财务岗（同一数据，只把专业需求填到专业栏 + 技能用本体词） | 5/5 | **0.91** | 无 | 对口（高置信） |

> **更正（2026-09-23）**：财务岗那条"缺必需技能"要分清成分——其中 4 项（用友、财务分析、
> 金蝶、预算管理）**是真实缺失**（岗位要、候选人确实没有，报出来不算错）；只有 1 项
> `成本控制` 是**错报**：JD 写"成本核算"，而当时本体把 `成本核算` 当作 `成本控制` 的别名，
> 归一后二者合并，于是候选人明明有"成本核算"却被判"缺成本控制"。
> 这条错报已在 v1.7 用领域包修正（`成本核算` 升为独立条目，别名迁移被显式报告）。
> 保留这段更正，是因为**当初"5 条全是误报"的判断本身不准确**——
> 把口径说准比把问题说大更有用；而且"真实缺失"与"错报"在处理上是两回事：
> 前者要 HR 判断，后者要改词表。

两处结论都不对：数字化岗判"无法判定"，财务岗判"对口"——
**后者尤其危险**：9 项需求只有 1 项（成本核算）被收录，两侧各自只剩这同一个残留项，
交集恰好非空，于是判出"对口"。**结论由"哪一项碰巧被收录"决定，而不是由人岗是否真的匹配决定。**

### 13.2 根因：三件本该分开的事被绑在一起

| 层 | 现状实现 | 问题 |
|---|---|---|
| 抽取层（简历 → 结构化字段） | 模型 + 自由文本 | 无问题 |
| 归一化层（同义词归并） | 本体白名单（214 技能 / 395 别名） | **成了全局瓶颈** |
| 方向判定层（对不对口） | 技能 → 大类映射，`major_match` 把「其他」剔除 | 剔除后判定退化（见上表） |
| 岗位需求层（JD 尺子） | 只有 `education_min`/`years_min`/`skills_required`/`preferred.skills` | **专业需求无处安放** |

一句话：**"能不能匹配"被绑定在"本体有没有收录"上**。
本体是封闭词表，岗位是开放世界，二者永远追不上——所以在当前架构下，
"新增岗位要一直扩本体吗"的答案是**是，而且永远扩不完**。

### 13.3 三条不变式（把"加内容"换成"建机制"）

**不变式 1 —— 未收录 ≠ 判错（最高优先）**
未归类项不得被剔除出判定。改法：
① 已归类项走"大类交集"通道；② 未归类项走"文本/语义相似"兜底通道
（等值 → 前缀 → 编辑距离 → 字符 n-gram；向量服务恢复后可升级为语义相似）；
③ 判定输出附**置信度**：大类覆盖率高 → 高置信；靠兜底通道 → 低置信，并显式注明
"本体未收录 N 项，判定可靠性下降"。
④ `grade` 的"缺必需技能"只对本体已收录项报警，未收录项另列"岗位自定义要求"，不扣分。
> 不变式 1 单独就能消除三类错误结论：假"对口"、假"无法判定"、假"缺技能"。

**不变式 2 —— 大类层用通用学科体系，一次建成永久够用**
现行 `MAJOR_HINTS` 是 5 个**业务领域**大类（软件·材料·机械·化学·管理）+ 领域关键词，
是业务词表，必然漏（实测 18 项漏 4：凝聚态物理、仪器科学与技术、仪器仪表工程、无损检测）。
改为两级**官方体系**：
- 顶层：**学科门类**（哲学·经济学·法学·教育学·文学·历史学·理学·工学·农学·医学·管理学·艺术学·交叉学科）
  ＋《职业分类大典》大类；
- 二级：一级学科名（材料科学与工程、仪器科学与技术、计算机科学与技术、应用经济学、工商管理…）。

财务岗 → 管理学门类 → 工商管理 / 应用经济学，**天然有位置**，无需为财务新增任何"领域大类"。
关键性质：**学科目录有限、稳定、官方收口**（14 门类 + 100 余一级学科），
不像"技能"是无限集合——"一次建成永久够用"只在这一层成立。新增行业只往二级学科表加条目（纯数据）。

**不变式 3 —— JD 存原文 + 结构化，专业需求做一等字段**
新增 `major_required` / `major_preferred`，值为**通用学科名**。
匹配不依赖本体收录，而是：目录精确名 → 别名/曾用名 → 二级归属（"材料学"⊂"材料科学与工程"）
→ 归一化（全半角、括号方向、简称）。
**专业作为独立维度呈现，默认不参与硬性淘汰**（材料物理去做工艺是常态），
只给 HR 一个显式的"专业是否在需求清单内"标识与理由。

### 13.4 纯规则 / 纯模型 / 混合

| 方案 | 新领域零配置 | 可复现·可审计 | 调用成本 | 涉军/信创可控 | 主要风险 |
|---|---|---|---|---|---|
| 纯规则（现状） | ❌ 必须先扩本体 | ✅ 完全可复现 | 极低 | ✅ 可全内网 | 封闭词表追不上新领域 |
| 纯模型打分 | ✅ 直接可跑 | ❌ 同输入不同分 | 高（每人一次大模型调用） | ⚠️ 需私有化大模型 | 分数漂移、无法向评审解释"为什么 82 分"、易受提示词影响 |
| **混合（推荐）** | ✅ 兜底可用 | ✅ 分数由规则汇总 | 中 | ✅ 可全内网 | 需设计好分工 |

**推荐分工（关键：模型不做算分）**
1. **模型只做"抽取 + 受约束的归一化"**：输入 JD 原文与简历文本，输出结构化 JSON
   （技能、专业、学历、年限、证书）。**技能允许自由文本**——不要它从 214 条里挑，
   那正是瓶颈的来源。
2. **归一化交给"词表 + 相似度"**：先查本体（快路径），查不到走相似度兜底（慢路径），
   仍查不到就**原样保留**并标注"自定义项"。
3. **算分交给规则**：分数 = 规则项加权汇总，每一项都能点开看到证据原文。
   "为什么 62 分"永远可解释——这是院内评审能认的前提。
4. **模型另出一份自然语言理由**，仅供参考，不参与排序。

理由：分数必须**可复现、可审计、可离线**（信创 / 涉军硬要求）。
纯模型打分会让同一份简历两次不同分，评审无法解释；
而"抽取出错"比"打分漂移"好修得多。

### 13.5 落地步骤（每步可独立验收）

| 步骤 | 内容 | 改动面 | 验收标准 |
|---|---|---|---|
| P0-a | 不变式 1：`major_match` 不再剔除未归类项，加兜底相似度通道 + 置信度 + 未收录计数；`grade` 对未收录项不误报 | `tier.py` | 财务岗不再判"对口"（应判低置信"部分对口/无法判定"并注明未收录 8 项）；数字化岗不再"无法判定" |
| P0-b | 不变式 3：JD 加 `major_required`/`major_preferred`，界面可填，专业独立维度展示 | `server.py` `ui.py` `jd.json` | HR 在界面填专业需求后，报告里出现"专业：在/不在需求清单内"+理由 |
| P1 | 不变式 2：`MAJOR_HINTS` 换两级通用学科目录（数据文件，可热更新），补仪器仪表/理学/无损检测盲区 | `tier.py` + 新数据文件 | 18 项专业需求全部能判出门类；财务岗判"管理学" |
| P2 | "领域包"机制：一个 JSON 声明"某领域常用技能 + 别名 + 归属学科"，HR/管理员随时导入，不改代码 | `db.py` + 界面 | 导入财务领域包后，9 项命中外 ≥7 项 |
| P2（依赖） | 把本地 embedding 服务起起来（现降级 `local-hash-v1`） | 环境 | `cli.py doctor` 无降级提示；语义兜底召回可用 |

### 13.6 判断改造是否成功的唯一标准

**新增一个财务岗位，需要写代码吗？**
- 需要写代码（扩本体 / 改词表）→ 架构未解耦；
- 只需 HR 在界面录一份 JD → 架构已解耦。

三者要区分开：**技能（无限，靠自由文本 + 兜底，不预录）**、
**学科（有限且官方，一次性建成）**、**岗位（业务，本就该每岗位录一份，是业务动作不是开发动作）**。
—— 所以"难道要把所有岗位都加进去吗"的答案是否定的：
要建的是**扩展机制**，不是**扩展内容**。
